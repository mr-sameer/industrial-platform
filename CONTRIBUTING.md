# Contributing

## Branching & commits

- Branch names: `<type>/<short-description>` (e.g. `feat/health-check-endpoint`).
- Commits and PR titles follow [Conventional Commits](https://www.conventionalcommits.org/):
  `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`, `ci:`, `build:`,
  `perf:`, `revert:`. Enforced by `.github/workflows/pr-title-lint.yml`.
- Rebase your branch onto `main`/`develop` before opening a PR; avoid merge
  commits in feature branches.

## Before opening a PR

1. Read [`docs/standards/coding-standards.md`](docs/standards/coding-standards.md)
   and [`docs/standards/naming-conventions.md`](docs/standards/naming-conventions.md).
2. If your change touches an API response shape, confirm it matches
   [`docs/standards/api-response-standard.md`](docs/standards/api-response-standard.md).
3. If your change is architecturally significant (new service, new data
   store, reversing a prior ADR), write a new ADR in `docs/adr/` — copy the
   structure of an existing one (Context / Decision / Alternatives
   considered / Consequences). Don't edit an existing accepted ADR's
   decision — mark it superseded and add a new one instead.
4. Run the full local check suite for whatever you touched:
   ```bash
   pnpm lint && pnpm typecheck && pnpm turbo run test --filter=web
   cd apps/api && ruff check . && ruff format --check . && mypy app && pytest --cov=app
   cd apps/mobile && flutter analyze && flutter test
   ```
5. Fill out the PR template checklist (`.github/pull_request_template.md`).

## Code review expectations

- At least one approval required before merge.
- Reviewers check: does this follow the standards docs, is it tested, does
  it avoid scope creep beyond what the PR title promises, and — for
  anything touching `apps/api` — does it keep routes thin per the
  service-layer convention in `coding-standards.md`.

## Adding a new package to the JS/TS workspace

```bash
mkdir packages/<name> && cd packages/<name>
# add package.json with "name": "@platform/<name>", extend @platform/tsconfig
# and @platform/eslint-config as shown in existing packages/* directories
```

Then add it to `apps/web/package.json` dependencies as `"@platform/<name>": "workspace:*"`
if the web app needs to consume it.

## Adding a database migration (Module 2+)

```bash
cd apps/api
alembic revision --autogenerate -m "add <thing>"
alembic upgrade head
```

Review the autogenerated migration by hand before committing — Alembic's
autogeneration is a starting point, not a guarantee of correctness.

## Questions

Open a discussion or reach out to the maintainers listed in the repository
settings before starting significant architectural work not already
covered by an existing ADR.
